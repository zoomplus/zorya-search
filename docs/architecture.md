# Архитектура Zorya Search

`zorya-search` — библиотека поиска и извлечения контекста. Её вызывает уже существующий клиент через SDK или MCP. Пакет не создаёт агенты, сессии, память, планы и задачи, не меняет prompt клиента и не редактирует файлы автоматически.

## Слои

Карты потоков и отказных ветвей собраны в [обзоре service flows](service-flows.md). Обновляй карту соответствующего модуля при изменении поведения или контракта; она описывает исходный код, а не статус публикации или acceptance.

Текущие исходники выделяют отдельный `project-text` слой и таблицы `zorya_project_text_*` для документации, правил и навыков; он делит с кодовым индексом identity и базу владельца, но не сбрасывает code/knowledge data. Подробности доступны в [руководстве по тексту проекта](project-text.md) и [карте модуля](../src/project-text/README.md). Эта capability включена в preview `v0.1.7`, но отсутствует в GitHub archive `v0.1.6`.

- `src/core/` содержит контракты, проверки и оркестрацию поиска и индексации ([карта](../src/core/README.md)).
- `src/storage/` реализует embedded и PostgreSQL хранение ([карта](../src/storage/README.md)). Владение соединением зависит от фабрики. `openEmbeddedDatabase` владеет созданной базой и блокировкой каталога, а `createCodeIndex` получает заимствованную базу и не закрывает её.
- `src/code/` индексирует текст репозитория и выдаёт lexical или гибридные code hits ([карта](../src/code/README.md)). Результаты привязаны к repository, worktree, snapshot и content hash.
- `src/providers/` адаптирует embedding, rerank, web discovery/read и classification API ([карта](../src/providers/README.md)).
- `src/context/` формирует ограниченный контекст кода или web-источников; preview `v0.1.7` (source `3be35fd`) добавляет opt-in Jev-backed reuse context поверх существующего `CodeIndex` ([карта](../src/context/README.md)).
- `src/visual/` выполняет отдельный opt-in поиск по явно переданным вызывающим кодом текстовым или графическим references ([карта](../src/visual/README.md)). Он не снимает экран и не оценивает корректность UI.
- `src/mcp/` публикует инструменты для существующего MCP-клиента ([карта](../src/mcp/README.md)). `src/daemon/` предоставляет локальный HTTP endpoint ([карта](../src/daemon/README.md)), удалённый OAuth-режим и IP/CIDR allowlist режим `v0.1.11`; оба удалённых режима используют loopback binding. Внешний TLS proxy и, для OAuth, authorization server настраивает владелец. Stdio proxy подключается к уже запущенному локальному daemon. `serve-remote-ip` не включает providers и не отменяет серверные principal/root/operation grants; его resource обязателен. Публичный target `https://startzorya.com/mcp/search` ограничен web-only profile/grant, без проектных данных или read/index grants.

Публичные subpaths задаёт `package.json`. Используй только документированные exports и типы установленной версии. SDK, MCP transport и client setup — разные уровни: установленная библиотека сама не подключает инструменты к редактору или текущему чату.

В preview `v0.1.7` (source `3be35fd`) classification и reuse используют один закреплённый Jev Decisions port: `typesafe/jev-1.14` через TypeSafe без fallback. MCP reuse требует `read` и `classify`; клиент владеет prompt, моделью, памятью, workflow и решением по возвращённым кандидатам. Функция отсутствует в историческом GitHub archive `v0.1.6`; проверь [страницу релиза](https://github.com/zoomplus/zorya-search/releases/tag/v0.1.7) для фактической доступности соответствующего asset. См. [руководство Jev](jev-classification.md).

## Поток запроса

Клиент задаёт разрешённый корень и формулирует поиск. Runtime проверяет доступ, актуальность поколения и профиль, затем обращается к индексу или настроенным provider adapters. Ответ содержит доступные identity, источники, диапазоны, ranking metadata, degradation или ошибки. Клиент проверяет найденный кандидат и сам решает, как использовать его. Содержимое источника и выходы классификатора остаются недоверенными данными.

Кодовый индекс различает snapshot identity, `CodeHit.contentHash` отдельного chunk и hash полного файла, возвращаемый при чтении. Перед применением результата клиент сверяет snapshot и текущий источник. Web discovery ссылки и чтение документа — отдельные этапы. Для visual retrieval клиент явно передаёт reference; score показывает только близость модели.

Один вызов `createCodeContext` для штатного `CodeIndex` открывает ограниченную временем read-scope одного root и snapshot. Вызывающий агент может явно ограничить запрос `language` и эвристическим `sourceKind` (`implementation`, `tests`, `documentation` или `all`); отсутствующий фильтр сохраняет прежнюю полную выдачу. Нефильтрованные поисковые запросы внутри операции переиспользуют строки корпуса и подготовленные лексические термы; статистика BM25 пересчитывается для каждого набора фильтров, чтобы не менять ранжирование. Если операция начинается с фильтрованного запроса, лексическая подготовка ограничена его результатами. SQL не выбирает `vector_json`, когда текущий поиск работает lexical. Обязательные диапазоны и найденные источники читаются с проверкой свежего содержимого, а перед возвратом повторно проверяются fingerprint дерева и Git identity. Scope закрывается после завершения физической работы и не сохраняет строки или подготовленные термы после запроса. Пользовательские реализации `CodeIndex`, которые предоставляют только четыре прежних read-порта, продолжают вызываться прежним способом. При явном `includeRelated` штатный индекс обходит существующие `zorya_code_imports` по уровням в обе стороны, ограничивая глубину, узлы и рёбра без полной выгрузки графа. Достигнутые пути становятся фильтром одного обычного поиска; расстояние по графу не превращается в синтетический relevance score. Scoped graph-read участвует в общем snapshot scope и физическом join его операций.

Индексацией владеет runtime: `startIndexing` создаёт или переиспользует один активный job на root, а `cancelIndexing` принимает только точные root/job IDs и возвращается после физического завершения. Все источники индексации — sync API, очередь background jobs и watcher — проходят общий per-root lock, поэтому смена поколения не конкурирует сама с собой; sync API сохраняет сигнал отмены и ожидаемый результат. MCP admission переживает закрытие запроса клиента. Очередь ограничена числом configured roots и `indexing.maxConcurrentRoots`; завершённые статусы хранятся ограниченно в памяти процесса. `indexStatus` работает через отдельный ограниченный и отслеживаемый control pool, включает точный job DTO, номер попытки и фактические chunks/checkpoints, без выдуманных процентов. Перезапуск или закрытие runtime отменяет и физически присоединяет принадлежащую работу.

При включённом watch daemon сначала проверяет конфигурацию и открывает HTTP endpoint, затем индексирует корни и запускает watcher; watcher запуск для каждого root привязан к стабильному completion promise, включая очередь. Изменения во время первого прохода повторно сверяются с ограниченным числом попыток. Timeout попытки повторяется только после наблюдаемого прироста durable checkpoint; постоянные ошибки provider завершают job. Watcher приостанавливает периодический повтор после постоянной ошибки либо трёх ошибок подряд и возобновляется по файловому событию или явному успешному job. Job registry не сохраняется в БД; после аварии новая явная admission продолжает от durable batch checkpoints.

## Модели и деградация

Lexical поиск работает без ключа и не вызывает embedding или rerank. Dense-поиск требует совместимого профиля provider/model/dimensions/input type/chunker version. При отсутствии или несовпадении профиля hybrid code-поиск возвращает lexical деградацию с причиной. Ошибка самого HTTP-вызова embedding или rerank пробрасывается, а не маскируется автоматическим lexical fallback. Web-context отдельно может вернуть частичный результат и `errors` по этапам.

Для Mechanism сверены независимые профили retrieval: `voyageai/voyage-code-4` с размерностью 1024 и reranker `voyageai/rerank-2.5-lite`; отдельный visual профиль использует `voyageai/voyage-multimodal-3.5` с размерностью 1024. Это клиентская конфигурация, не значения по умолчанию или встроенный выбор Search. Профили code и visual не взаимозаменяемы, visual включается отдельно. Search принимает только выбранные клиентом и явно переданные материалы; он не захватывает экран.

## Текущий контракт

Лексический поиск работает без ключа. Dense-поиск и reranking требуют совместимого профиля и отправляют выбранные фрагменты соответствующему provider adapter. Профили и пространства данных разделены, а каждый результат сохраняет identity источника и известные ограничения. Включение конкретной функции зависит от конфигурации владельца и grants клиента; см. [матрицу возможностей](capabilities.md).

## Локальный workspace bridge (`v0.1.11`)

`src/bridge/` связывает локальный Codex stdio MCP client с отдельным центральным BridgeServer. На каждый MCP call client проверяет per-call native conversation ID и canonical `process.cwd()`, затем формирует workspace identity из client ID и пути. `PWD`, ambient `CODEX_THREAD_ID`, статический config cwd и installation/server path не служат запасными источниками identity. Server хранит снимок источника отдельно по client/workspace identity и открывает существующий Search runtime.

Source-free calls используют null snapshot и не передают проект. Явные `index_repository`, `start_indexing`, `index_code_symbols`, `index_project_text` сначала синхронизируют изменившиеся байты, затем вызывают существующий MCP tool с исходными аргументами. Сама передача не индексирует и не запускает provider. Code/project-text search/read/context не синхронизируют файлы автоматически: client сверяет local manifest до и после вызова и возвращает typed stale refusal при изменении. Отмена и статус фоновой индексации не требуют повторного upload; ownership ограничен conversation identity.

Два resource targets имеют разные grants: `https://startzorya.com/mcp/search` предназначен только для публичных web-source tools с `web:{}` runtime profile и `web` grant, без project roots/data или `read`/`index` grants; `https://startzorya.com/mcp/search/workspace` предназначен для отдельной частной workspace-конфигурации с machine credential и client/CIDR policy. Лимиты передачи, exclusion policies и evidence boundaries описаны в [руководстве workspace bridge](workspace-bridge.md).
