# Архитектура Zorya Search

`@zorya/search` — библиотека поиска и извлечения контекста. Её вызывает уже существующий клиент через SDK или MCP. Пакет не создаёт агенты, сессии, память, планы и задачи, не меняет prompt клиента и не редактирует файлы автоматически.

## Слои

- `src/core/` содержит контракты, проверки и оркестрацию поиска и индексации.
- `src/storage/` реализует embedded и PostgreSQL хранение. Владение соединением зависит от фабрики. `openEmbeddedDatabase` владеет созданной базой и блокировкой каталога, а `createCodeIndex` получает заимствованную базу и не закрывает её.
- `src/code/` индексирует текст репозитория и выдаёт lexical или гибридные code hits. Результаты привязаны к repository, worktree, snapshot и content hash.
- `src/providers/` адаптирует embedding, rerank, web discovery/read и classification API.
- `src/context/` формирует ограниченный контекст кода или web-источников и вызывает классификатор по критериям клиента.
- `src/visual/` выполняет отдельный opt-in поиск по явно переданным вызывающим кодом текстовым или графическим references. Он не снимает экран и не оценивает корректность UI.
- `src/mcp/` публикует инструменты для существующего MCP-клиента. `src/daemon/` предоставляет HTTP endpoint и владельца runtime. Stdio proxy подключается к уже запущенному daemon.

Публичные subpaths задаёт `package.json`. Используй только документированные exports и типы установленной версии. SDK, MCP transport и client setup — разные уровни: установленная библиотека сама не подключает инструменты к редактору или текущему чату.

## Поток запроса

Клиент задаёт разрешённый корень и формулирует поиск. Runtime проверяет доступ, актуальность поколения и профиль, затем обращается к индексу или настроенным provider adapters. Ответ содержит доступные identity, источники, диапазоны, ranking metadata, degradation или ошибки. Клиент проверяет найденный кандидат и сам решает, как использовать его. Содержимое источника и выходы классификатора остаются недоверенными данными.

Кодовый индекс различает snapshot identity, `CodeHit.contentHash` отдельного chunk и hash полного файла, возвращаемый при чтении. Перед применением результата клиент сверяет snapshot и текущий источник. Web discovery ссылки и чтение документа — отдельные этапы. Для visual retrieval клиент явно передаёт reference; score показывает только близость модели.

Один вызов `createCodeContext` для штатного `CodeIndex` открывает ограниченную временем read-scope одного root и snapshot. Поисковые запросы внутри операции переиспользуют строки корпуса; SQL не выбирает `vector_json`, когда текущий поиск работает lexical. Обязательные диапазоны и найденные источники читаются с проверкой свежего содержимого, а перед возвратом повторно проверяются fingerprint дерева и Git identity. Scope закрывается после завершения физической работы и не сохраняет строки после запроса. Пользовательские реализации `CodeIndex`, которые предоставляют только четыре прежних read-порта, продолжают вызываться прежним способом.

Индексацией владеет runtime: `startIndexing` создаёт или переиспользует один активный job на root, а `cancelIndexing` принимает только точные root/job IDs и возвращается после физического завершения. Все источники индексации — sync API, очередь background jobs и watcher — проходят общий per-root lock, поэтому смена поколения не конкурирует сама с собой; sync API сохраняет сигнал отмены и ожидаемый результат. MCP admission переживает закрытие запроса клиента. Очередь ограничена числом configured roots и `indexing.maxConcurrentRoots`; завершённые статусы хранятся ограниченно в памяти процесса. `indexStatus` работает через отдельный ограниченный и отслеживаемый control pool, включает точный job DTO, номер попытки и фактические chunks/checkpoints, без выдуманных процентов. Перезапуск или закрытие runtime отменяет и физически присоединяет принадлежащую работу.

При включённом watch daemon сначала проверяет конфигурацию и открывает HTTP endpoint, затем индексирует корни и запускает watcher; watcher запуск для каждого root привязан к стабильному completion promise, включая очередь. Изменения во время первого прохода повторно сверяются с ограниченным числом попыток. Timeout попытки повторяется только после наблюдаемого прироста durable checkpoint; постоянные ошибки provider завершают job. Watcher приостанавливает периодический повтор после постоянной ошибки либо трёх ошибок подряд и возобновляется по файловому событию или явному успешному job. Job registry не сохраняется в БД; после аварии новая явная admission продолжает от durable batch checkpoints.

## Модели и деградация

Lexical поиск работает без ключа и не вызывает embedding или rerank. Dense-поиск требует совместимого профиля provider/model/dimensions/input type/chunker version. При отсутствии или несовпадении профиля hybrid code-поиск возвращает lexical деградацию с причиной. Ошибка самого HTTP-вызова embedding или rerank пробрасывается, а не маскируется автоматическим lexical fallback. Web-context отдельно может вернуть частичный результат и `errors` по этапам.

Для Mechanism сверены независимые профили retrieval: `voyageai/voyage-code-4` с размерностью 1024 и reranker `voyageai/rerank-2.5-lite`; отдельный visual профиль использует `voyageai/voyage-multimodal-3.5` с размерностью 1024. Это клиентская конфигурация, не значения по умолчанию или встроенный выбор Search. Профили code и visual не взаимозаменяемы, visual включается отдельно. Search принимает только выбранные клиентом и явно переданные материалы; он не захватывает экран.

## Доказательства и ограничения

Интегрированный source snapshot `34253f64e4918f17591816c81cc515fc9a313109` прошёл package gates: 181/181 тестов, без ошибок и пропусков. Архив размером 230 388 байт с 214 файлами установлен в отдельном consumer; аудит обнаружил все 16 обязательных файлов, не нашёл битых локальных ссылок или путей к приватному хосту. Настоящий Codex CLI 0.163.0 прошёл 11 локальных проверок с двумя клиентами: созданная настройка запускала установленную команду из другого рабочего каталога, клиенты использовали общий текущий snapshot, watcher опубликовал новое поколение после изменения исходника, а владелец службы был штатно остановлен.

Отдельный smoke выполнен через установленный пакет и OpenRouter на десяти синтетических файлах и одном сгенерированном изображении. Все восемь физических вызовов получили успешный ответ; поиск по коду поставил ожидаемый файл первым, а одиночная visual-проверка вернула переданную ссылку. Известная стоимость составила $0.00011708, неизвестных вызовов нет. Это ограниченная проверка wire/runtime и одного fixture, а не оценка естественно-языкового поиска на реальном репозитории, визуального качества или широкой точности.

Отдельные сценарии индекса подтвердили повторное использование 32 успешно встроенных партий после отмены: из 84 файлов после перезапуска было отправлено только 52, без повторения завершённых входов. Обновление сохранило прежние 24 863 code chunks, их digest и checksum миграции `code_001`, добавив следующую миграцию. Эти данные относятся к Search-owned индексу, не к базе знаний игры.

Пакет не опубликован и не подключён к текущему чату. Права Windows, hosted авторизация и регистрация клиента, Witcher, широкое качество поиска и полная программа приёмки не проверены; шесть парных запусков остаются `0/6`. Не переноси локальные результаты на другие версии и исходные снимки.
