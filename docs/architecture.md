# Архитектура Zorya Search

Zorya Search — отдельный MIT-пакет `@zorya/search`. Он предоставляет повторно используемое ядро поиска, которое могут вызывать библиотечные потребители, CLI и будущий MCP-интерфейс. Наличие одного способа вызова не означает подключения остальных.

## Принятая основа

В текущем снимке есть общее ядро и специализированные слои:

- `src/core/` — контракты поиска, проверка входов, оркестрация операций, reindex и обслуживание.
- `src/storage/` — интерфейсы БД, embedded/PostgreSQL адаптеры, репозитории, миграции, очередь и ANN индекс.
- `src/code/` — отдельная идентичность и жизненный цикл индекса кода, перечисление файлов, разбиение TS/JS, лексический ranking, watcher и чтение источника.
- `src/providers/` — контракты и адаптеры embeddings/rerank, web discovery/read и классификации.
- `src/context/` — ограниченный контекст кода, web-поиск и вызов классификатора. Эти адаптеры связывают индекс и порты провайдера с DTO для вызывающего приложения; они не управляют его prompt или памятью.
- `src/visual/` — отдельный opt-in поиск по явно переданным текстовым или графическим reference. Его временный индекс не захватывает экран и не выполняет pixel QA.

Потребитель передаёт модели и источники через порты; Search валидирует и координирует вызовы, а хранилище сохраняет индекс и результаты. Корневой export `@zorya/search` предоставляет core и владельца embedded-БД; он не реэкспортирует runtime-модули контекста, provider adapters, code index или visual search. Специализированные subpaths `@zorya/search/code`, `@zorya/search/providers`, `@zorya/search/context`, `@zorya/search/context/web`, `@zorya/search/context/classify` и `@zorya/search/visual` отделяют эти поверхности. Импортируй только используемые subpaths и проверяй их по `package.json`. Подробный пример владения и каталог методов — в [справочнике SDK](sdk.md).

## Поток поиска по коду

Индексатор получает разрешённый корень, определяет repository/worktree/snapshot/content hash, выбирает допустимые файлы, создаёт chunks и сохраняет lexical индекс. Векторный путь включается только при настроенном совместимом профиле. Для TS/JS применяются AST/symbol chunks и поддерживаемое разрешение импортов; другие типы могут использовать явно обозначенный текстовый fallback. `CodeHit.contentHash` относится к содержимому конкретного chunk; `readSource.contentHash` — к полному текущему файлу. Это разные уровни идентичности.

Результат связывает путь и диапазон строк с исходной идентичностью и профилем. Если файл или snapshot изменился, `readSource` завершается ошибкой; успешный ответ сообщает `stale: false`. `relatedCode` возвращает наблюдаемые imports/importedBy и похожие hits; это контекст, а не решение о размещении кода или рефакторинге.

## Поток контекста, web и классификации

`createCodeContext` принимает уже созданный `CodeIndex` и формирует ограниченные текстовые разделы для запроса и необязательных feature queries. `mustInclude` позволяет вызывающей стороне указать обязательные пути или диапазоны, а `includeRelated` отдельно включает дополнительные imports и похожие фрагменты. Результат содержит исходную идентичность, диапазоны, хеш полного прочитанного файла, происхождение ранжирования и сведения о деградации. Он возвращается вызывающей стороне; Search сам не внедряет его в контекст агента.

Web-контекст использует `WebSource` для обнаружения URL и чтения документов, а provider contracts — для embeddings и необязательного rerank. Сетевой поиск/read и каждый профиль модели настраиваются независимо; частичные ошибки этапов отражаются в результате. Ошибка embedding/rerank в web-поиске записывается в `errors`; lexical evidence может остаться в выдаче. Для code hybrid ошибки самих вызовов embedding/rerank пробрасываются, а не подменяются lexical fallback. Классификация принимает категории и критерии вызывающей стороны, проверяет DTO и возвращает допустимые метки, необязательные оценки/evidence, abstention и uncertainty. Детали factory и сигнатур перечислены в [справочнике SDK](sdk.md); будущие CLI/MCP интерфейсы не следует считать принятыми до соответствующей волны.

Web-текст и результаты провайдера — недоверенные данные. Search не исполняет их, не изменяет prompt или память вызывающего агента и не выполняет действия на основе score.

## Хранение, согласованность и деградация

Каждое пространство эмбеддингов изолируется по provider, model, dimensions, input type и другим параметрам профиля. Индекс кода привязывается к repository, worktree, snapshot и хешу содержимого. Смена профиля требует отдельного совместимого пространства или переиндексации.

Индекс должен публиковать только актуальное завершённое поколение. Отмена или изменение источника не делает старый индекс свежим; watcher дополняется периодической сверкой. Явный lexical режим не вызывает embedding/rerank-модели и доступен без облачного ключа. Для `CodeIndex` запрос `hybrid` без настроенных моделей или с несовместимым профилем/snapshot возвращает lexical результат с явной причиной деградации; при передаче models нужен валидный embedding profile, а profile без models недопустим при создании индекса. Ошибка самого вызова code embedding/rerank пробрасывается и не переключается автоматически на lexical. В web context ошибки embedding/rerank отражаются в частичном результате, и lexical ranking может сохраниться.

Search не владеет сессиями и памятью клиента, а владение соединением зависит от API. `openEmbeddedDatabase` владеет созданным PGlite engine и эксклюзивной блокировкой каталога: повторное открытие того же каталога сейчас завершается отказом. `connectPostgres` владеет созданным им пулом; `wrapPostgresPool` и legacy wrapper заимствуют пул/соединение вызывающей стороны и не закрывают его. `createCodeIndex` получает только `QueryableDatabase`; его `close()` останавливает ресурсы индекса и ожидает принадлежащие ему операции, но не закрывает переданную БД. Планируемый единый daemon как владелец embedded datadir ещё не реализован. Совместимость legacy схем и данных потребителя сохраняется; миграция или удаление данных требуют отдельного решения и проверки.

## Визуальный поиск

`createVisualSearch` по умолчанию выключен. Включённый экземпляр принимает только явно переданный вызывающей стороной текстовый reference или байты одного изображения с metadata и SHA-256; индекс эфемерный и очищается при закрытии. Без embedding режима text retrieval сравнивает `reference.text`; `screen`, `state` и `breakpoint` используются как точные фильтры. Запрос картинкой в таком режиме не поддержан. При настроенном embedding-порте переданная картинка может быть запросом, но similarity остаётся оценкой близости модели, а не визуальным QA или подтверждением качества. Пакет не получает скриншоты самостоятельно.

## Интерфейсы и статус

Исходники baseline экспортируют core, `code`, `providers`, `context`, два специализированных context subpath и `visual` согласно package exports. Приёмка каждого слоя и незавершённые волны перечислены в [плане реализации](implementation-plan.md); наличие export не означает, что весь план или отдельный optional visual scope принят. CLI, MCP stdio/HTTP, единый daemon, мастер настройки и Assistant adapter не следует описывать как готовые части до их отдельной приёмки. Модульные тесты и mock providers не подтверждают работу с живым провайдером или реальным MCP-клиентом.

Статус волн и внешние квитанции ведутся в [плане реализации](implementation-plan.md). Указанная в плане приёмка относится только к своему snapshot и охвату. Установка пакета не подключает инструменты к текущему чату автоматически.
