# Возможности и границы версий

Эта страница отделяет доступный архив GitHub-релиза от возможностей текущих исходников. GitHub archive `v0.1.6` остаётся доступным артефактом; npm registry пакет не опубликован. Новые возможности source candidate не следует считать частью установленного архива.

## Что делает Search

Zorya Search индексирует разрешённые файлы и предоставляет существующему клиенту API поиска и чтения. Ответы содержат найденный текст или структурированные кандидаты, пути и диапазоны, идентичность snapshot и, где применимо, сведения об усечении и ошибках. Это помогает вызывающему агенту проверять сведения по исходнику. Search не пишет в репозиторий, не выполняет автоматический ремонт и не подменяет агента.

Обычный code search по умолчанию лексический и не вызывает внешние модели. Владелец может отдельно настроить code embedding и reranking: профиль Mechanism использует специализированную `voyageai/voyage-code-4` и `voyageai/rerank-2.5-lite`. Для web-поиска Brave отвечает за поиск ссылок; текст страниц затем читается отдельно. Настройка code-профиля не включает web-поиск, а web embedding или reranker не заменяет code-профиль. Смотрите [справочник SDK](sdk.md), [MCP](mcp.md) и [профили Voyage](voyage-profiles.md).

Новые symbol API включают `findCodeSymbols` / `find_code_symbols`, `findCodeReferences` / `find_code_references` и `traceCodeCalls` / `trace_code_calls`. Поиск по `symbolId` точный; `enclosing` задаёт полный диапазон строк и один точный путь файла. Эти фильтры пересекаются с остальными. `fileLineCount` помогает определить точное число строк штатно прочитанного файла; поле optional, поэтому старый адаптер без него не доказывает полноту короткого файла. Эти additions не выполняют скрытую индексацию metadata.

## Логический контекст в текущих исходниках

`includeLogical: true` добавляет `logicalContext` в `getCodeContext` или `get_code_context`. Без opt-in поле отсутствует и прежний ответ сохраняется. Это настройка одного запроса: клиент сам выбирает, когда она полезна. Она независима от `includeRelated`, которое отвечает за import graph и похожие фрагменты.

Логический контекст начинает с текущих результатов поиска и может включать подтверждённые символы, статические contracts, callees, callers и test owners, если metadata содержит соответствующие связи. Точность связывания опирается на AST symbol identity и известные имена. При ведущих комментариях или imports поиск может восстановить символ по точному имени/qualified name; если имя неоднозначно или связь не подтверждена, ответ сохраняет source fallback или omission вместо утверждения, что найденный диапазон — вся функция.

Глубина в блоке обозначает расстояние от найденного seed: seed — `0`, непосредственное ребро — `1`, второй outgoing hop — `2`. Роль блока показывает, почему он включён; seed может оставаться seed даже при наличии связи с другим блоком.

### Бюджеты и полнота

| Ограничение | Значение |
| --- | ---: |
| Бюджет текста контекста по умолчанию | 24 000 символов |
| Схема MCP `get_code_context` | не более 24 000 символов |
| SDK `CodeContextLimits.maxChars` | до 100 000 символов при явной настройке |
| Строк в одной секции/чтении | не более 200 |
| Seeds | не более 8 |
| Logical blocks | не более 24 |
| Проверяемых references на seed | не более 50 |
| Чтений исходника | не более 120 |
| Сохраняемых записей omission | не более 80, с отдельными счётчиками пропуска и усечения |

Длинное тело может быть представлено несколькими секциями. `block.complete` описывает покрытие исходного блока, а не полноту всего репозитория или анализа. `analysisComplete`, состояние `logicalContext`, coverage, limits, omissions и snapshot-bound continuation сообщают границы результата. Continuation содержит `path`, `lineStart`, `lineEnd`, `snapshotId`; его читают через `readSource` вместе с тем же `root` в SDK либо через `read_source` с тем же `rootId` в MCP. Чтение отвергнет несовпадающий или устаревший snapshot. Не переносите диапазон на новый snapshot и не запускайте автоматический backfill при чтении.

Результат не обещает полноту runtime-вызовов: `runtimeCallCoverage` имеет значение `not_claimed`. Статический анализ не доказывает динамический dispatch, dependency injection, framework wiring или семантическую корректность. Если связи не найдены, это не доказывает, что их нет. Читайте актуальный исходник и проверяйте его в задаче.

Пределы для полного включения больших диапазонов намеренно отражаются как omissions/partial coverage. Их нельзя трактовать как отрицательный ответ. Отдельно `includeRelated` сохраняет собственные настройки и не включается автоматически вместе с `includeLogical`.

## Индексируемые файлы и документы

Текущая политика перечисляет распространённые языки исходников и часть текстовых конфигураций, а также Markdown `.md` и `.mdx`. Она **не** индексирует файлы редакторских правил `.mdc` и обычные `.txt`. Классификатор `sourceKind` может распознавать расширение как категорию документации, но это само по себе не означает, что формат входит в список индексируемых файлов.

Отдельная функция семантических embeddings по материалам репозитория — документации, правилам и skills — запрошена, но не реализована. Нынешний поиск по поддерживаемому Markdown не означает, что есть отдельный профиль или продуктовая возможность для corpus документации. Не рекламируйте эту работу как готовую.

## Где установить и проверить

Для пользователя доступен GitHub archive `v0.1.6`, устанавливаемый по командам из [начала работы](getting-started.md). Функции, отмеченные «текущие исходники», не входят в этот архив. npm registry публикации нет. Подробные контракты и примеры текущих типов приведены в [SDK](sdk.md); перечень транспортных инструментов и их разрешения — в [MCP](mcp.md).
