# План реализации Zorya Search

**Статус: принятый план; волны 3–9 ещё не выполнены. Волна 2 интегрирована и принята в указанном ниже охвате.** Отдельный продукт создаётся как `@zorya/search` в новом репозитории. Здесь будут общее ядро поиска по коду и веб-источникам, порты провайдеров, CLI, фоновая служба и инструменты MCP. Assistant подключается через адаптер; существующее поведение поиска игры и знаний сохраняется. Аудит исходников `Zorya Mechanism` описан в [матрице переноса](mechanism-reuse.md); исходный репозиторий не изменяется.

## Уточнение объёма от 2026-10-31

MCP-инструменты Search вызываются существующими агентами. Search не создаёт внутренних агентов и не подменяет модель, инструкции, личность, память или рабочий процесс вызывающего агента. В частности, сюда не входят реализации PM/Dev/QA-ролей, планировщик, реестр задач, согласование областей полномочий, исполнение заданий или автоматическое редактирование кода. Не копировать agent implementations из Mechanism. Состав функций ограничен поиском кода и веб-источников, embeddings, reranking, классификацией и связанными инструментами поиска. Библиотека должна работать напрямую из SDK и как CLI; MCP — дополнительный интерфейс вызова.

Поиск и классификация возвращают кандидатов с источниками, границами и неопределённостью. Вызывающий агент решает, как использовать результат. `getCodeContext` принимает необязательные бюджет и список обязательных путей от вызывающей стороны, если ей нужен такой режим; он не внедряет результат в prompt автоматически и не меняет контекст агента за его спиной. Query embedding cache является общим кэшем по запросу, области поиска, профилю модели и снимку источника; task stamping и фабричный жизненный цикл задач не требуются.

## Факты, решения и открытые детали

**Подтверждённые требования пользователя:** отдельные репозиторий и npm-пакет; мастер настройки облачного провайдера; вызов инструментов чата и программирования через MCP/plugins/skills; одно ядро для всех сервисов и поиска по web и коду. Требования к интерфейсу и хранилищу не означают, что компоненты уже реализованы. Есть аудит исходников `Mechanism`, но его код и тесты не приняты как готовые компоненты Search. Core второй волны разрабатывается в отдельном worktree; проверка пакета на этом этапе не заменяет интегрированную приёмку.

**Проектные решения главного оркестратора:** локальный лексический поиск имеет ограниченный объём и работает без облачного ключа; дополнительные службы построения векторов, повторного ранжирования, сетевого поиска и классификации подключаются через строгие порты. PGlite выбран как возможная локальная база, PostgreSQL — как серверная. Каждый индекс векторов относится к конкретным repository/worktree/snapshot и профилю модели. Отмена, устаревшее поколение или ошибка провайдера не позволяют опубликовать частичный/устаревший индекс как актуальный. Ранжирование и классификация возвращают подсказки, а не полномочия или действия.

**Открыты до реализации соответствующей волны:** окончательные публичные имена и сигнатуры API (предварительные операции ниже); точные схемы и миграции; конфигурируемые профили провайдеров/моделей и лимиты; подробности мастера настройки и клиентских конфигураций; дополнительные языки и визуальный поиск. Новые провайдеры должны подключаться через расширяемые конфигурационные профили, а не требовать вшитого списка поставщиков. Ни один незакреплённый выбор нельзя подавать как уже доступную возможность.

## Архитектурная граница

```text
Клиенты и сервисы
  Assistant adapter | CLI | MCP stdio / Streamable HTTP | будущие plugins/skills
                               |
                    общий Search API / daemon
          +--------------------+-------------------+
          |                    |                   |
    Контекст кода        Источники сети       Классификация
  lexical + dense       lexical + provider     labels/evidence
  symbols + relations   search/read source    uncertainty
          |                    |
          +------- context fusion / provenance --+
                               |
      порты провайдеров: embeddings / reranker / web retrieval / classification
                               |
       лексическое ядро поиска + порты хранилища
           PostgreSQL server | optional local PGlite
```

Публичный интерфейс должен сохранять источник и границы результата: `repoId`, `worktreeId`, snapshot/content hash, путь, line start/end, при наличии symbol/language, профиль provider/model/space, источник score/provenance и признаки stale/degraded. Предварительные имена операций: `indexRepository`, `watchRepository`, `searchCode`, `getCodeContext`, `relatedCode`, `indexStatus`, `classify`; поиску по web нужны соответствующие порты поиска и чтения источников. `classify` принимает от вызывающей стороны категории и критерии, возвращает только метки из предложенного набора, доступные оценки, основания и неопределённость. Схема должна позволять отсутствие оценки, если провайдер её не выдаёт. `getCodeContext` может принять необязательные бюджет и список обязательных путей. Ни одна операция не меняет prompt, инструкции или иное состояние агента. Search возвращает текст источников и результаты классификации как недоверенные данные, не исполняет их и не использует для изменения конфигурации вызывающего агента; интерпретация остаётся за вызывающей стороной. Имена и схемы здесь предварительные, а не утверждённый API.

Индекс строится в ограниченной очереди; публикация snapshot атомарна только после повторной проверки корня, идентичности источника и текущего поколения. Отменённая операция или изменение источника не должны опубликовать устаревший snapshot. За наблюдением за файлами следует периодическая сверка на случай пропущенных событий. Смена профиля модели создаёт отдельную версию пространства и требует переиндексации; несовместимые векторы смешивать нельзя. Ключ кэша векторов запроса включает текст запроса, область поиска, профиль модели и snapshot источника; обязательного идентификатора задачи нет. Числовые векторы не передаются в prompt JSON.

Для кода TS/JS планируется разбиение по AST/symbol и поддерживаемый resolver; остальные языки сначала получают явный текстовый запасной режим. Граф ограничивается реально разрешаемыми зависимостями; нельзя заявлять полный call graph для всех языков. Файлы отбираются с учётом gitignore, исключений для секретных/сгенерированных/бинарных файлов, ограничения размера и проверки realpath scope. Это снижает случайный риск, но не обещает обнаружить все секреты в остальных исходниках. Мастер настройки заранее сообщает, что облачный провайдер может получить переданный фрагмент кода; автоматическая отправка полного checkout не подразумевается.

Локальный лексический режим работает без ключей. PGlite выбран главным оркестратором как возможная локальная база; PostgreSQL предназначен для серверного режима. Фоновая служба Search владеет только индексами и заданиями индексации, но не сессиями агентов или их памятью. Один процесс службы владеет каждым datadir; несколько клиентов обращаются к нему, а не открывают одну embedded-базу параллельно. Мастер настройки и диагностика состояния показывают конфигурацию и сохраняют секреты в безопасной локальной конфигурации; ключи нельзя включать в ссылки быстрой настройки. HTTP-интерфейс MCP ограничивается явно разрешённым списком корней/workspace и аутентификацией; локальный stdio также обязан соблюдать границы корня. Та же библиотека доступна напрямую через SDK и CLI без MCP.

Главный оркестратор владеет анализом, архитектурными решениями, проверкой, тестированием и Git-интеграцией. Новые пути ниже относятся к плану и не подтверждают существование реализации.

### Волна 3 — индексатор кода и адаптеры провайдеров (две раздельные реализации, затем передача общих файлов)

- **Роль и цель:** два исполнителя Luna, каждый high reasoning и `fork_turns=none`; один строит индекс и связи кода, второй — строгие адаптеры облачных провайдеров. Главный оркестратор начинает Wave 3 только после принятия основы Wave 2.
- **Файловое владение:** два отдельных worktree. Исполнитель индекса кода владеет `src/code/**`, `test/code/**`: идентичность repository/worktree, content hashes, поколения snapshot, AST/symbol-части TS/JS, разрешение импортов, ограниченное наблюдение и сверка файлов, удаление/переименование и версии профиля; отдельная новая схема базы кода, без наследования legacy game SQL. Исполнитель провайдеров владеет `src/providers/**`, `test/providers/**`: порты облачных embeddings/rerank, web-поиска и классификации, проверка ответов, ограниченная параллельность, сроки, отмена, бюджеты и типизированные ошибки. Идентификаторы провайдеров задаются расширяемыми профилями конфигурации. Web-чтение через удалённый MCP ограничивает допустимые схемы URL и число перенаправлений, повторно проверяет DNS-адреса и блокирует частные адреса согласно разрешениям владельца. Вызывающий клиент не может расширить разрешённые сервером корни или область доступа. Эти исполнители не меняют общие index/package/lock/API и не редактируют файлы друг друга.
- **Зависимости и параллелизм:** два исполнителя могут работать параллельно после приёмки Wave 2 только в раздельных worktree и каталогах. После их работы один назначенный исполнитель Luna получает последовательное владение всеми общими путями интеграции в Waves 3–5: `src/index.ts`, package exports/metadata/scripts, lockfile и schema/migrations. Только этот исполнитель меняет эти файлы после параллельных работ и выдачи владения; параллельные исполнители их не редактируют. Главный оркестратор проверяет и интегрирует diff, но не пишет техническую реализацию сам.
- **Ожидаемые артефакты:** жизненный цикл индекса кода и изолированные тестовые примеры; интерфейсы/адаптеры провайдеров с моками и изолированной проверкой неверных размерностей/индексов, NaN, срока и отмены. Незаявленных реальных обращений к провайдерам нет.
- **Gate:** главный оркестратор проверяет контракт, отмену, атомарную публикацию, устаревшие версии, удаление/переименование/worktree, несовместимые пространства векторов и точные схемы ошибок; затем проверяет и интегрирует общие exports/dependencies. Качество облачного поиска проверяется отдельно и не выводится из тестов с mock-ответами.

### Волна 4 — контекст, классификация и дополнительные способы поиска (последовательно)

- **Роль и цель:** исполнитель Luna (high) работает после принятия Waves 2–3. Сначала реализует слияние лексических и векторных рангов, контекст и классификацию; затем — визуальный поиск как последовательную часть той же утверждённой волны, после проверки предыдущей части главным оркестратором.
- **Файловое владение:** `src/context/**`, `test/context/**` — reciprocal-rank fusion (RRF), повторное ранжирование, необязательный вызываемый клиентом бюджет и список обязательных путей для `getCodeContext`, provenance и `relatedCode`. Этот инструмент возвращает похожие реализации, зависимости и подтверждающие источники; вызывающий агент сам решает, переиспользовать ли код, рефакторить его или выбрать размещение. Владелец реализует `classify`: вызывающий задаёт допустимые категории и критерии, настроенный адаптер вызывает выбранный профиль провайдера/модели, результат проходит строгую проверку допустимых меток и включает доступные оценки, основания и неопределённость. Операция ограничена бюджетом, отменяема и не меняет инструкции или prompt агента. В следующем последовательном подэтапе тот же владелец редактирует `src/visual/**`, `test/visual/**`; визуальные данные получают отдельное пространство и явную настройку opt-in во время выполнения. Нужные общие exports, package metadata, lockfile и migrations меняет только назначенный в Wave 3 Luna-владелец общей интеграции, последовательно и после передачи этих путей; главный оркестратор только проверяет и интегрирует.
- **Зависимости и параллелизм:** подэтапы выполняются последовательно. Визуальный поиск начинается после проверки и принятия контекстного поиска в пределах уже утверждённого объёма. API-порты Wave 3 остаются неизменной зависимостью.
- **Ожидаемые артефакты:** результаты с источниками, границами, профилем и признаками degraded/stale; тесты некорректного provider index, устаревшего snapshot, обязательных файлов, нескольких наборов feature-требований и лексического запасного режима. Для визуальной части — opt-in работа с image/text reference, screen/state/breakpoint filters без автоматического индексирования скриншотов.
- **Gate:** главный оркестратор проверяет сохранение явно запрошенных путей при ограниченном бюджете, разнообразие результатов, покрытие заданных классификационных меток, строгую схему ответа, явную деградацию и происхождение. Ни score, включая высокий rerank, ни результат классификации/визуального поиска не дают разрешения на действие, не меняют prompt и не запускают редактирование кода. Визуальный поиск остаётся поиском, а не pixel QA или проверкой pass/fail.

### Волна 5 — CLI, MCP и настройка фоновой службы

- **Роль и цель:** исполнитель Luna (high) подключает CLI и MCP к принятому интерфейсу модулей core/context/provider.
- **Файловое владение:** `src/cli/**`, `src/mcp/**` и принадлежащие им тесты: мастер настройки/диагностики, инкрементальная фоновая служба, которая владеет индексами и заданиями индексации, несколько клиентов workspace, MCP stdio и Streamable HTTP. Существующие агенты вызывают MCP-инструменты Search; Search не создаёт агентские сессии и не управляет их памятью или рабочим процессом. MCP открывает поиск кода, web-поиск, `relatedCode`, `getCodeContext` и `classify`. Требуемые технические изменения общих package scripts/exports/config/lock остаются у того же назначенного Luna-владельца интеграции из Wave 3 и выполняются последовательно после выдачи ему этих путей; главный оркестратор проверяет и интегрирует, но не редактирует реализацию.
- **Зависимости и параллелизм:** после принятой Wave 4; один исполнитель. После реализации и проверки главный оркестратор проводит реальную проверку отдельным MCP-клиентом: индексирует рабочее дерево Zorya Assistant и проверяет, что поиск находит цепочку `packages/search-service` → `packages/game-runtime/src/app/backend-composition-search.ts` → `search-port.ts`. Точные команды, снимок и критерии этой проверки главный оркестратор закрепляет перед запуском. Это проверка SDK/MCP-клиента, а не подключение инструментов к текущему чату ChatGPT.
- **Ожидаемые артефакты:** безопасная установка node и настройка с описанием резервного копирования/восстановления, локальный запуск без ключа, диагностика, ограниченные переиндексация/наблюдение за файлами, MCP server/tools и HTTP allowlist/auth для корневых каталогов.
- **Gate:** главный оркестратор проверяет единственный процесс-владелец embedded datadir при параллельных клиентах, перезапуск, отмену и несколько workspaces; настоящий MCP-клиент действительно вызывает поиск и находит заданную цепочку Assistant. Проверить также прямой вызов библиотеки/CLI без MCP. Установка или настройка пакета сама по себе не означает подключение к конкретному клиенту. Ключи не входят в ссылки быстрой настройки. Результат фиксируется отдельно от будущей проверки текущей интеграции инструментов в чат.

### Волна 6 — русская документация, навыки и инструкции агента

- **Роль и цель:** автор прозы Luna, high, пишет долговечную пользовательскую документацию, руководства CLI/MCP, skills и локальный набор правил агента; главный оркестратор сверяет факты и принимает результат.
- **Файловое владение:** назначенные корневые `README`/`docs/**`, `skills/**` и локальный набор инструкций агента в новом Search repo. Не перезаписывать пользовательские глобальные `AGENTS.md`; не менять реализацию из волны документации. Документы должны отделять уже доступное от запланированного.
- **Зависимости и параллелизм:** каркас и согласованная терминология могут оформляться отдельно; окончательные инструкции связываются с реально принятой Wave 5 и её проверками. Автор документации не меняет файлы других владельцев.
- **Ожидаемые артефакты:** русские инструкции вызова инструментов, индексирования и обновления, чтения источников, настройки провайдера, ошибок и degraded/stale состояния, а также границы приватности и доступа. Документация поясняет, что Search возвращает текст, метки и score как данные, не исполняет их и не меняет настройки вызывающего агента; их интерпретация остаётся за клиентом. Она не устанавливает обязательный порядок работы агента или глобальную политику.
- **Gate:** главный оркестратор сверяет команды и интерфейсы с принятым кодом, проверяет ссылки и статусы, убеждается, что локальные правила не заменяют глобальные пользовательские правила. Документация не называет пакет подключённым к текущему клиенту или опубликованным.

### Волна 7 — совместимость с Zorya Assistant через адаптер

- **Роль и цель:** исполнитель Luna (high) интегрирует отдельный Search API через узкий адаптер после успешной проверки пакета-потребителя и принятой среды выполнения. Главный оркестратор владеет областью межрепозиторной интеграции и приёмкой.
- **Файловое владение:** выделенный Assistant worktree; только адаптер/сборка зависимостей и регрессионные тесты в согласованных production/test путях. Нельзя переписывать `SearchModels`, `WebSource`, `KnowledgeRepository`, менять существующее пользовательское поведение или менять Mechanism. События, `ElementError`, SQL/history и настройки embedding-модели остаются контрактом. Модель, инструкции, личность, память и рабочий процесс вызывающего Assistant-агента не изменяются.
- **Зависимости и параллелизм:** после Wave 5 и передачи пакета, последовательно и изолированно. Никаких одновременных писателей в одном Assistant checkout.
- **Ожидаемые артефакты:** адаптер-обёртка, граница включения/настройки и регрессионные результаты; без сброса базы и скрытой смены провайдера. Luna использует результаты реального MCP-поиска из Wave 5 как контекст интеграции `@zorya/search`, сохраняя существующие знания, события и настройки моделей.
- **Gate:** главный оркестратор сравнивает старое/новое поведение, schema/history и настройки; проверяет, что интеграция не создаёт агентских сессий, не меняет инструкции и не вызывает поиск скрытно. После изменений и перезапуска главный оркестратор повторяет запросы через MCP-клиент и запускает согласованные проверки Assistant. Исходники Assistant проверяются отдельно от установленной Windows версии, устройств и качества провайдера. Этот план не разрешает миграцию самого Mechanism.

### Волна 8 — комплексные проверки, релевантность и эксплуатационные границы

- **Роль и цель:** главный оркестратор запускает и сверяет проверки на зафиксированном интегрированном snapshot; исполнитель Luna исправляет найденные дефекты только в уже выделенном ему worktree и в согласованной области. После Wave 5 он также организует ограниченный парный пилот доступности MCP для задач завершения кода в Assistant.
- **Файловое владение:** главный оркестратор владеет свидетельствами и тестовой оркестрацией; исправления возвращаются активному владельцу соответствующего кода. Отобранные корпуса и свидетельства хранятся вне проекта в утверждённом каталоге; персональные исходники и секреты не становятся тестовыми данными.
- **Зависимости и параллелизм:** после Waves 2–7; проверки выполняются на одном зафиксированном снимке. Лексический, плотный векторный, объединённый и повторно ранжированный поиск сравниваются на одном фиксированном корпусе. Для парного пилота главный оркестратор заранее фиксирует снимок Assistant, шесть представительных задач (поиск нужной логики, исправление дефектов и изменения совместимости), их критерии приёмки, точные запросы и пути. Только после этой фиксации запускаются пары в отдельных worktree и чистых контекстах.
- **Ожидаемые артефакты:** проверка установленного пакета в чистом потребителе и локального лексического поиска без сети; сценарии первичной индексации, изменения/удаления/переименования, веток/worktree, исключения секретных путей, перезапуска, отмены и одновременных вызовов MCP, PGlite и серверного PostgreSQL. Для отобранных запросов считаются Recall@k, MRR, nDCG, p50/p95 latency, вызовы провайдеров, tokens и cost; неизвестная стоимость явно остаётся unknown. Пилот включает шесть пар запусков двух исполнителей Luna (high, `fork_turns=none`) в отдельных worktree и чистых контекстах, с одинаковыми инструкциями и лимитом времени: контроль использует обычные доступные инструменты, парный вариант — те же инструменты плюс Search MCP. Между парными запусками не передаются решения. Главный оркестратор сохраняет фактические diff и тесты, корректность, регрессии, время, повторы, поисковые вызовы, доступные token-метрики и стоимость с явным unknown при отсутствии данных; холодную и прогретую индексацию учитывает раздельно.
- **Gate:** главный оркестратор фиксирует точный snapshot, квитанции запусков, охват и ограничения. Не изобретать универсальный порог точности; сравнить режимы и зафиксировать выводы отдельно. Шесть пар — ограниченный пилот, а не универсальное доказательство качества; улучшение заранее не предполагается. Синтетические проверки отделены от выполнения реальных задач завершения Assistant. Проверки с моками/без провайдера и реальные облачные вызовы разделены. Приёмка исходников Assistant не квалифицирует Windows, устройства или установщик. Проверить, что продукт не создаёт внутренних PM/Dev/QA-агентов, задач/планов, механизмов согласования полномочий или автоматического редактирования кода; не запускает скрытые поисковые вызовы и не меняет prompt, модель, память или инструкции вызывающего агента. Интеграция через SDK/MCP-клиент не доказывает наличие инструментов в текущем интерфейсе чата. Если интеграция не завершена, полная приёмка остаётся false.

### Волна 9 — готовность к публикации и итоговая сводка

- **Роль и цель:** главный оркестратор проверяет пакет, среду выполнения и документацию, подтверждает готовность к выпуску и при наличии необходимого доступа выполняет запланированную публикацию. Luna не публикует и не выполняет Git-записи.
- **Файловое владение:** главный оркестратор владеет квитанциями выпуска и интеграцией Git; исполнители не выполняют несогласованные операции Git/публикации. Существующие до задачи ветки, worktree и изменения не удаляются.
- **Зависимости и параллелизм:** только после принятия всех предыдущих gates; последовательно. Публикация начинается после подтверждения доступа и точного состава пакета.
- **Ожидаемые артефакты:** проверяемая интеграция, сверка tarball и скачанных байтов по хешу, CI/ref/status и очистка только принадлежащих задаче временных материалов; один итоговый отчёт с выполненным, непроверенным и исключённым объёмом.
- **Gate:** доказать факт публикации, если она выполнялась, и сверить полученные байты. Если нет доступа к учётной записи или репозиторию, указать точное препятствие; не утверждать, что пакет опубликован, подключён к клиенту или полностью принят. Удалять только worktree и артефакты, созданные этой задачей, после сохранения и проверки нужных свидетельств; историческое состояние сохраняется.

## Приёмка и недопустимые выводы

- API/библиотека, CLI и MCP проверяются как разные точки входа в одно ядро; установка `npm` не равна успешному вызову MCP из конкретного клиента чата или программирования.
- Локальные fixtures и mock providers подтверждают логику только в пределах своего охвата. Реальный провайдер, качество поиска, стоимость и настройка клиента подтверждаются отдельными квитанциями.
- Search передаёт найденное содержимое и выход классификатора как данные и не исполняет их и не применяет к конфигурации агента. Их интерпретация остаётся за вызывающей стороной. Параметры клиента не могут расширить серверные allowlist корней и web-доступа.
- Поиск даёт источники, кандидатов и контекст для вызывающего сервиса. Он не доказывает истинность ответа, не выдаёт полномочий, не решает удалять/переписывать код и не заменяет пользовательское подтверждение.
- Идентичность snapshot и branch/worktree должна быть видна в выдаче и проверена перед возвратом результата. Не сообщать старые части кода как актуальные после удаления/изменения или смены профиля.
- Итоговый отчёт отдельно указывает подтверждённое, заблокированное, непроверенное и исключённое; результаты только по исходникам или fixtures не выдаются за полную приёмку.
