## Wave 5: runtime, MCP, CLI и client validation

Волны выполняются последовательно; общий источник истины — Search SDK/runtime, а локальный embedded datadir имеет одного владельца. MCP transports являются клиентами этого runtime/daemon и не открывают собственные копии PGlite для того же каталога.

1. **Wave 5.1 — SDK runtime и owner config (scoped source accepted).** Роль: прямой Luna technical implementer по активированному `resource_exhausted` fallback, `gpt-6-luna/high`; root — архитектурный владелец и review/integration. Workspace `/root/.codex/worktrees/zorya-search-runtime-20261031`, ветка `feat/search-runtime-20261031`, базовый source `c112e179ead154c9f5fa50d242f0dd5c7426f823`. Owned paths: `src/runtime/**`, `test/runtime/**`, `package.json` (runtime subpath), только type exports в `src/index.ts`, этот план. Runtime валидирует versioned config, canonical allowlisted roots, provider secret references, открывает один embedded DB, создаёт индексы/context wrappers и физически отменяет и дожидается owned operations перед DB close. Сигнал фабрики отменяет только запуск; после успешного возврата включённые watcher принадлежат runtime до `close()`, а их reconcile и обычные операции имеют собственные сигналы, timeout и root guard. Файл `secrets.json` берётся из явного `configDir`; чтение ограничено открытым fd и размером, короткие чтения дочитываются, POSIX symlink и не-regular file отклоняются, метаданные и права проверяются по fd. На Windows проверка POSIX mode bits не является проверкой ACL; настройщик должен ограничивать ACL средствами Windows. Root review потребовал покрытие сигналов context/classify, strict operation DTO, owner cancellation/close, bounded watcher reconcile, credentials/config-file boundaries, typed redaction и production-provider composition. Root-owned package gates: 151/151 тест, typecheck, build, diff-check и pack PASS на Node 24.12.0/pnpm 9.15.9; source stable. Отдельные actual PGlite boundary checks — 4/4 PASS. Квитанции привязаны в статусе выше. Живых запросов к внешним провайдерам нет; MCP transport/client dogfood не входит в Wave 5.1.
2. **Wave 5.2 — MCP transports и singleton daemon (scoped-PASS, интегрировано в `fa3185ce364abcc9df2a65775cd31f9566e0e8f5`).** Принятый source commit `635918a12cc25eebe0e30fab3c3601ea893e4cf6`; root evidence `root-evidence/wave5-mcp-verification-v1` фиксирует 162/162 теста и isolated installed-consumer checks. `@zorya/search/mcp` предоставляет поиск-кандидат инструменты и stdio transport; `@zorya/search/daemon` владеет единственным runtime/embedded DB. ## Уточнение объёма от 2026-10-31

MCP-инструменты Search вызываются существующими агентами. Search не создаёт внутренних агентов и не подменяет модель, инструкции, личность, память или рабочий процесс вызывающего агента. В частности, сюда не входят реализации PM/Dev/QA-ролей, планировщик, реестр задач, согласование областей полномочий, исполнение заданий или автоматическое редактирование кода. Не копировать agent implementations из Mechanism. Состав функций ограничен поиском кода и веб-источников, embeddings, reranking, классификацией и связанными инструментами поиска. Библиотека должна работать напрямую из SDK и как CLI; MCP — дополнительный интерфейс вызова.

Поиск и классификация возвращают кандидатов с источниками, границами и неопределённостью. Вызывающий агент решает, как использовать результат. `getCodeContext` принимает необязательные бюджет и список обязательных путей от вызывающей стороны, если ей нужен такой режим; он не внедряет результат в prompt автоматически и не меняет контекст агента за его спиной. Query embedding cache является общим кэшем по запросу, области поиска, профилю модели и снимку источника; task stamping и фабричный жизненный цикл задач не требуются.

## Факты, решения и открытые детали

**Подтверждённые требования пользователя:** отдельный репозиторий и npm-пакет; мастер настройки облачного провайдера; вызов инструментов чата и программирования через MCP/plugins/skills; одно ядро для всех сервисов и поиска по web и коду. Core, code, context/web/classify, visual и runtime исходники приняты главным оркестратором только в областях Wave 2–5.1 и по указанным квитанциям; это не означает завершения daemon/MCP, CLI/setup, Assistant integration или всей программы. Есть аудит исходников `Mechanism`, но его код и тесты не приняты как готовые компоненты Search.

**Проектные решения главного оркестратора:** локальный лексический поиск имеет ограниченный объём и работает без облачного ключа; дополнительные службы построения векторов, повторного ранжирования, сетевого поиска и классификации подключаются через строгие порты. PGlite выбран как возможная локальная база, PostgreSQL — как серверная. Каждый индекс векторов относится к конкретным repository/worktree/snapshot и профилю модели. Отмена, устаревшее поколение или ошибка провайдера не позволяют опубликовать частичный/устаревший индекс как актуальный. Ранжирование и классификация возвращают подсказки, а не полномочия или действия.

**Открыты до реализации соответствующей волны:** окончательные публичные имена и сигнатуры API (предварительные операции ниже); точные схемы и миграции; конфигурируемые профили провайдеров/моделей и лимиты; подробности мастера настройки и клиентских конфигураций; дополнительные языки и визуальный поиск. Новые провайдеры должны подключаться через расширяемые конфигурационные профили, а не требовать вшитого списка поставщиков. Ни один незакреплённый выбор нельзя подавать как уже доступную возможность.

**Принятые точки входа в package.json:** корневой импорт `@zorya/search` предоставляет core; `@zorya/search/code` — индекс кода; `@zorya/search/providers` — адаптеры; `@zorya/search/context`, `@zorya/search/context/web`, `@zorya/search/context/classify` и `@zorya/search/visual` — отдельные принятые Wave 4 подмаршруты; `@zorya/search/runtime` — принятая Wave 5.1 owner runtime/config фабрика. Корневой entry экспортирует относящиеся типы без eager runtime imports. В `package.json` указана лицензия MIT согласно подтверждённому выбору пользователя. Отдельные подмаршруты и acceptance MCP/client остаются разными областями.

## Архитектурная граница

```text
Клиенты и сервисы
  Assistant adapter | CLI | MCP stdio / Streamable HTTP | будущие plugins/skills
                               |
                    общий Search API / daemon
          +--------------------+-------------------+
          |                    |                   |
    Контекст кода        Источники сети       Классификация
  lexical + dense       lexical + provider     labels/evidence
  symbols + relations   search/read source    uncertainty
          |                    |
          +------- context fusion / provenance --+
                               |
      порты провайдеров: embeddings / reranker / web retrieval / classification
                               |
       лексическое ядро поиска + порты хранилища
           PostgreSQL server | optional local PGlite
```

Публичный интерфейс должен сохранять источник и границы результата: `repoId`, `worktreeId`, snapshot/content hash, путь, line start/end, при наличии symbol/language, профиль provider/model/space, источник score/provenance и признаки stale/degraded. Предварительные имена операций: `indexRepository`, `watchRepository`, `searchCode`, `getCodeContext`, `relatedCode`, `indexStatus`, `classify`; поиску по web нужны соответствующие порты поиска и чтения источников. `classify` принимает от вызывающей стороны категории и критерии, возвращает только метки из предложенного набора, доступные оценки, основания и неопределённость. Схема должна позволять отсутствие оценки, если провайдер её не выдаёт. `getCodeContext` может принять необязательные бюджет и список обязательных путей. Ни одна операция не меняет prompt, инструкции или иное состояние агента. Search возвращает текст источников и результаты классификации как недоверенные данные, не исполняет их и не использует для изменения конфигурации вызывающего агента; интерпретация остаётся за вызывающей стороной. Имена и схемы здесь предварительные, а не утверждённый API.

Индекс строится в ограниченной очереди; публикация snapshot атомарна только после повторной проверки корня, идентичности источника и текущего поколения. Отменённая операция или изменение источника не должны опубликовать устаревший snapshot. За наблюдением за файлами следует периодическая сверка на случай пропущенных событий. Смена профиля модели создаёт отдельную версию пространства и требует переиндексации; несовместимые векторы смешивать нельзя. Ключ кэша векторов запроса включает текст запроса, область поиска, профиль модели и snapshot источника; обязательного идентификатора задачи нет. Числовые векторы не передаются в prompt JSON.

Для кода TS/JS планируется разбиение по AST/symbol и поддерживаемый resolver; остальные языки сначала получают явный текстовый запасной режим. Граф ограничивается реально разрешаемыми зависимостями; нельзя заявлять полный call graph для всех языков. Файлы отбираются с учётом gitignore, исключений для секретных/сгенерированных/бинарных файлов, ограничения размера и проверки realpath scope. Это снижает случайный риск, но не обещает обнаружить все секреты в остальных исходниках. Мастер настройки заранее сообщает, что облачный провайдер может получить переданный фрагмент кода; автоматическая отправка полного checkout не подразумевается.

Локальный лексический режим работает без ключей. PGlite выбран главным оркестратором как возможная локальная база; PostgreSQL предназначен для серверного режима. Фоновая служба Search владеет только индексами и заданиями индексации, но не сессиями агентов или их памятью. Один процесс службы владеет каждым datadir; несколько клиентов обращаются к нему, а не открывают одну embedded-базу параллельно. Мастер настройки и диагностика состояния показывают конфигурацию и сохраняют секреты в безопасной локальной конфигурации; ключи нельзя включать в ссылки быстрой настройки. HTTP-интерфейс MCP ограничивается явно разрешённым списком корней/workspace и аутентификацией; локальный stdio также обязан соблюдать границы корня. Та же библиотека доступна напрямую через SDK и CLI без MCP.

## Волны выполнения

Волны выполняются в порядке зависимостей. Код пишут назначенные исполнители `gpt-6-luna`, high reasoning, `fork_turns=none` в выделенных worktree. Действует переход после Cursor `resource_exhausted`; новые проверки и запуски Cursor запрещены. Главный оркестратор владеет анализом, архитектурными решениями, проверкой, тестированием и Git-интеграцией. Новые пути ниже относятся к плану и не подтверждают существование реализации.

**Уточнение последовательности от 2026-10-31:** после принятия Wave 5 главный оркестратор выполняет отдельную реальную проверку SDK/MCP-клиента на рабочем дереве Assistant; затем в Wave 7 Luna использует найденный контекст для интеграции, а главный оркестратор повторяет запрос после изменений и перезапуска. После Wave 7, в Wave 8, главный оркестратор проводит заранее специфицированный шестипарный пилот задач завершения Assistant. ### Волна 4 — контекст, классификация и дополнительные способы поиска (последовательно)

- **Роль и цель:** исполнитель Wave 4 — Luna high в fallback-режиме — работает после принятия Waves 2–3. Сначала реализует context/web/classification и получает review главного оркестратора; после этого последовательно реализует и проверяет визуальную часть.
- **Файловое владение:** `src/context/**`, `test/context/**` — `createCodeContext({index, limits?})` с `getCodeContext({root, query, featureQueries?, mustInclude?, includeRelated?, maxChars?, limit?, signal?})`, `relatedCode({root,path,symbol?,limit?,signal?})` и `close()`. Контекст выполняет поиск по базовому запросу и до 8 caller-defined feature queries, объединяет ранги RRF, сначала выбирает разные файлы и читает фрагменты только из того же snapshot. Обход импортов и похожих фрагментов включается только через `includeRelated: true`; по умолчанию он выключен, а `relatedCode` остаётся отдельной явной операцией. Обязательные caller-defined пути и строки обрабатываются прежде остальных; если они не помещаются в заданный бюджет целиком, API возвращает явную ошибку. Путь без строк означает ограниченный excerpt в пределах `maxRangeLines`; фактические line bounds и признак `truncated` показывают выданный охват, не утверждая, что прочитан весь файл. Совпадающие и пересекающиеся ranges объединяются в пределах лимита; если обязательные диапазоны рядом вместе длиннее лимита слияния, они остаются отдельными секциями без потери затребованных строк. Ответ содержит file content hash отдельно от candidate chunk hash, статусный `profileId` и provenance каждого ранга (query, lexical/dense/rerank rank, score и profile), бюджет, пропуски и причины деградации. У этого API нет скрытых обязательных проверок или автоматического изменения prompt. `createWebSearch` принимает имеющийся `WebSource`; лексический web-поиск работает без embedding, а embedding/reranker подключаются отдельно с явными профилями. Он возвращает канонические URL, фрагменты, content hashes, известные временные метки, rank provenance и типизированные частичные ошибки, без сгенерированного ответа. Число фрагментов ограничено `maxChunks`; при исчерпании лимита результат помечается частичной ошибкой бюджета. Неполный ответ reranker сохраняет оставшиеся fused-кандидаты. `createClassificationTool` вызывает настроенный `Classifier` с caller-provided labels и criteria, проверяет метки, evidence и uncertainty общим строгим DTO-валидатором и допускает только явную abstention согласно запросу. Все операции ограничены, отменяемы и возвращают недоверенные данные; используемые порты заимствованы и не закрываются фабриками.
- **Файловое владение (визуальный подэтап):** после review подэтапа context тот же исполнитель меняет `src/visual/**`, `test/visual/**`. `createVisualSearch` по умолчанию выключен и не требует profile или provider setup до явного opt-in; он хранит только ограниченные caller-provided reference metadata/vectors в памяти процесса. Caller предоставляет один image или text reference за операцию; библиотека не снимает/не скачивает скриншоты и не выполняет pixel QA. Embedding использует отдельный явный profile с ограниченной размерностью и явной идентичностью input type. Metadata-only поиск по image query завершается типизированной ошибкой `IMAGE_QUERY_UNSUPPORTED`; текстовый metadata fallback возвращает только реальные совпадения и помечен как lexical, без заявления о семантическом визуальном качестве. Raw image bytes не сохраняются. Update/delete/filter/abort используют ограниченный lifecycle; устаревший поиск отклоняется при конкурентном изменении, а закрытие присоединяется к активным операциям. Индексы не переживают закрытие/перезапуск.
- **Общие файлы:** только назначенный Wave 4 исполнитель владеет `package.json` (добавление export maps без новых dependencies), `src/index.ts` (type-only exports, без eager runtime import) и этим планом. Изменения provider-файлов допустимы только для узкого извлечения общей проверки результата классификации. Главный оркестратор проверяет и интегрирует; обычные core/storage/code/provider behavior остаются замороженными.
- **Зависимости и параллелизм:** сначала context/web/classification; после root review выполняется визуальный подэтап. Все подэтапы последовательны. API-порты Wave 3 остаются неизменной зависимостью; новые зависимости не требуются.
- **Ожидаемые артефакты:** результаты с источниками, границами, профилем и признаками degraded/stale; тесты некорректного provider index, устаревшего snapshot, обязательных файлов, нескольких наборов feature-требований и лексического запасного режима. Для визуальной части — opt-in работа с image/text reference, screen/state/breakpoint filters без автоматического индексирования скриншотов.
- **Gate:** главный оркестратор проверяет сохранение явно запрошенных путей при ограниченном бюджете, разнообразие результатов, покрытие заданных классификационных меток, строгую схему ответа, явную деградацию и происхождение. Ни score, включая высокий rerank, ни результат классификации/визуального поиска не дают разрешения на действие, не меняют prompt и не запускают редактирование кода. Визуальный поиск остаётся поиском, а не pixel QA или проверкой pass/fail.

Лексический, плотный векторный, объединённый и повторно ранжированный поиск сравниваются на одном фиксированном корпусе. Для парного пилота главный оркестратор заранее фиксирует снимок Assistant, шесть представительных задач (поиск нужной логики, исправление дефектов и изменения совместимости), их критерии приёмки, точные запросы и пути. Только после этой фиксации запускаются пары в отдельных worktree и чистых контекстах.
- **Ожидаемые артефакты:** проверка установленного пакета в чистом потребителе и локального лексического поиска без сети; сценарии первичной индексации, изменения/удаления/переименования, веток/worktree, исключения секретных путей, перезапуска, отмены и одновременных вызовов MCP, PGlite и серверного PostgreSQL. Для отобранных запросов считаются Recall@k, MRR, nDCG, p50/p95 latency, вызовы провайдеров, tokens и cost; неизвестная стоимость явно остаётся unknown. Пилот включает шесть пар запусков двух исполнителей Luna (high, `fork_turns=none`) в отдельных worktree и чистых контекстах, с одинаковыми инструкциями и лимитом времени: контроль использует обычные доступные инструменты, парный вариант — те же инструменты плюс Search MCP. Между парными запусками не передаются решения. Главный оркестратор сохраняет фактические diff и тесты, корректность, регрессии, время, повторы, поисковые вызовы, доступные token-метрики и стоимость с явным unknown при отсутствии данных; холодную и прогретую индексацию учитывает раздельно.
- **Gate:** главный оркестратор фиксирует точный snapshot, квитанции запусков, охват и ограничения. Не изобретать универсальный порог точности; сравнить режимы и зафиксировать выводы отдельно. Шесть пар — ограниченный пилот, а не универсальное доказательство качества; улучшение заранее не предполагается. Синтетические проверки отделены от выполнения реальных задач завершения Assistant. Проверки с моками/без провайдера и реальные облачные вызовы разделены. Приёмка исходников Assistant не квалифицирует Windows, устройства или установщик. Проверить, что продукт не создаёт внутренних PM/Dev/QA-агентов, задач/планов, механизмов согласования полномочий или автоматического редактирования кода; не запускает скрытые поисковые вызовы и не меняет prompt, модель, память или инструкции вызывающего агента. Интеграция через SDK/MCP-клиент не доказывает наличие инструментов в текущем интерфейсе чата. Если интеграция не завершена, полная приёмка остаётся false.

### Волна 9 — готовность к публикации и итоговая сводка

- **Роль и цель:** главный оркестратор проверяет пакет, среду выполнения и документацию, подтверждает готовность к выпуску и при наличии необходимого доступа выполняет запланированную публикацию. Luna не публикует и не выполняет Git-записи.
- **Файловое владение:** главный оркестратор владеет квитанциями выпуска и интеграцией Git; исполнители не выполняют несогласованные операции Git/публикации. Существующие до задачи ветки, worktree и изменения не удаляются.
- **Зависимости и параллелизм:** только после принятия всех предыдущих gates; последовательно. Публикация начинается после подтверждения доступа и точного состава пакета.
- **Ожидаемые артефакты:** проверяемая интеграция, сверка tarball и скачанных байтов по хешу, CI/ref/status и очистка только принадлежащих задаче временных материалов; один итоговый отчёт с выполненным, непроверенным и исключённым объёмом.
- **Gate:** доказать факт публикации, если она выполнялась, и сверить полученные байты. Если нет доступа к учётной записи или репозиторию, указать точное препятствие; не утверждать, что пакет опубликован, подключён к клиенту или полностью принят. Удалять только worktree и артефакты, созданные этой задачей, после сохранения и проверки нужных свидетельств; историческое состояние сохраняется.

## Приёмка и недопустимые выводы

- API/библиотека, CLI и MCP проверяются как разные точки входа в одно ядро; установка `npm` не равна успешному вызову MCP из конкретного клиента чата или программирования.
- Локальные fixtures и mock providers подтверждают логику только в пределах своего охвата. Реальный провайдер, качество поиска, стоимость и настройка клиента подтверждаются отдельными квитанциями.
- Search передаёт найденное содержимое и выход классификатора как данные и не исполняет их и не применяет к конфигурации агента. Их интерпретация остаётся за вызывающей стороной. Параметры клиента не могут расширить серверные allowlist корней и web-доступа.
- Поиск даёт источники, кандидатов и контекст для вызывающего сервиса. Он не доказывает истинность ответа, не выдаёт полномочий, не решает удалять/переписывать код и не заменяет пользовательское подтверждение.
- Идентичность snapshot и branch/worktree должна быть видна в выдаче и проверена перед возвратом результата. Не сообщать старые части кода как актуальные после удаления/изменения или смены профиля.
- Итоговый отчёт отдельно указывает подтверждённое, заблокированное, непроверенное и исключённое; результаты только по исходникам или fixtures не выдаются за полную приёмку.

### Wave 5.3 — CLI и пользовательская настройка (scoped-PASS, интегрирована)

CLI добавляет `zorya-search` с командами setup, doctor, index, search, context, foreground serve, stdio MCP, client-config и статусом/остановкой подтверждённого владельца службы. Он переиспользует строгую `runtimeConfigSchema`, SearchRuntime и MCP operations; отдельный поисковый алгоритм не вводится. Конфигурация и индекс располагаются в пользовательских путях вне индексируемых корней. По умолчанию применяется локальный lexical режим. Явный `--code-env` выбирает кодовый preset Voyage Code 4 (1024 dimensions) с rerank shortlist 30→8; независимый `--visual-env` включает visual preset Voyage Multimodal 3.5 (1024 dimensions, top 5) только по выбору пользователя. Оба профиля хранят ссылку на env-переменную, а общий runtime preset остаётся источником модели и размерности. Generic OpenAI-compatible embedding endpoint поддержан только как явно заданный custom profile; web reranker, classifier и web discovery настраиваются независимо. `search` без `--mode` использует профиль конфигурации, а lexical можно запросить явно. Watch — явный opt-in через `--watch` (интервал 250–60000 ms); daemon принимает клиентов после проверки базы, пока runtime-owned job индексирует корни. MCP `start_indexing`/`cancel_indexing` и `index_status` показывают ограниченное состояние jobs. CLI `index` по умолчанию ждёт terminal status, `--background` возвращает admission; прерывание отменяет только job, впервые созданный этим CLI-вызовом. Watch сверяет изменения после стартового прохода. Job registry остаётся в памяти процесса, а durable batch checkpoints позволяют новой явной admission продолжить после перезапуска.
